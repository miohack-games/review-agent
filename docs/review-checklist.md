# レビュー観点チェックリスト

汎用レビューエージェント（`agents/code-review.md`）が参照するレビュー観点の一覧です。
人間のレビュアーがそのまま読んでも使えるように、言語・フレームワークに依存しない形で書いています。

このチェックリストは**判断の土台**です。プロジェクト固有の規約（steering / `AGENTS.md` /
`CONTRIBUTING.md` / リンタ設定など）が存在する場合は、そちらを優先します。

---

## 前提：正しさをどう裏取りするか

「動けば正しい」は半分正しい。動作確認は最強の証拠だが、**試した範囲しか保証しない**。
だからレビューは、証拠の種類を意識して役割分担する。

| 手段 | 保証できること | 保証できないこと |
|------|----------------|------------------|
| 動作確認（手動） | 試した入力・状況での振る舞い | 試していない境界・異常系・競合 |
| テスト | テストが想定した入力空間での振る舞い（再現可能） | 想定から漏れた領域（＝書かれなかったテストの外） |
| 静的レビュー（このチェックリスト） | 実行で表面化しにくい問題の**疑い** | 疑いの確定（＝実行やテストで裏取りが要る） |

役割分担の原則：

- **静的レビューは「疑い」を挙げる** — 実行では出にくいもの（境界・認可・競合・仕様整合・
  秘密情報）を指摘する。
- **テストと動作確認が「疑い」を事実に変える** — 指摘したケースをテスト化して実行すれば白黒がつく。
  レビューの最も強い形は「静的な疑い → テストで裏取り」の組み合わせ。
- **正誤をコードから判断できないものは Question にする** — 期待値（オラクル）の妥当性や仕様の穴は
  人間の合意領域。勝手に正解を決めない。

リスクベースで力の入れどころを変える：低リスクな変更は動作確認＋テスト＋機械的レビューで十分。
お金・認可・データ破壊など**間違えると痛い箇所**に、レビューの重みを寄せる。

---

## 使い方

1. レビュー対象（差分・ファイル・PR）の変更範囲を把握する。
2. 変更が **フロントエンド / バックエンド / インフラ** のどの領域に該当するかを判定する
   （複数にまたがることもある）。
3. まず「領域横断」観点で見る。次に該当領域の観点を重ねる。
4. プロジェクト固有規約があれば、それを最優先の基準として突き合わせる。

指摘は重大度を添えて分類する。

| 重大度 | 意味 |
|--------|------|
| 🔴 Blocker | マージ前に必ず直すべき（バグ・脆弱性・データ破壊・規約違反でビルドが壊れる等） |
| 🟡 Major | 直すべき。放置すると保守性・信頼性に影響する |
| 🟢 Minor | 改善提案。好みや軽微な可読性の話 |
| 💬 Question | 意図の確認。正誤の判断がレビュアー側で付かないもの |

## レビューの姿勢（自己検証バイアスと一貫性への対策）

AI が実装したコードを AI がレビューすると、同じ盲点を共有しやすい。これを完全には消せないが、
姿勢で緩和する。人間がレビューする場合も、同じ姿勢が「自分が書いたコードの粗が見えない」問題に効く。

### 1. 「大丈夫」という主張を、結論ではなく検証すべき仮説として扱う

コード内コメント・コミットメッセージ・実装者の説明にある断定
（例:「件数は小さいので問題ない」「ここは起きない」「入力は必ず正しい」）を**根拠として受け取らない**。
その主張を疑い、**反例を1つ探す**。反例が見つからなければ「主張は妥当」と確認できるし、
見つかればそれが指摘になる。楽観的な前提こそ、最も見落としを生む。

### 2. 複数の視点で一巡する

素直に読む視点だけでは、素の生成で出る指摘しか出ない。少なくとも次の視点を切り替えて見る。

- **攻撃者の視点** — 不正な入力・権限のない操作・想定外の順序で、壊せないか。
- **データが桁違いに増えた視点** — 件数・同時実行が 1000 倍でも成り立つか。
- **引き継ぐ人の視点** — 事情を知らない別の開発者が、半年後にこのコードを安全に変更できるか。

### 3. 適用範囲を自己申告する

レビューの冒頭または末尾で、**どの観点を適用し、何を見ていないか**を明示する
（例:「セキュリティとデータ量の観点で見た。パフォーマンスの実測は未確認」）。
これにより、レビューのブレ（毎回見る所が変わる）を可視化し、見落とし範囲を人間が把握できる。

> これらは自己検証バイアスを**消す**ものではない。同じモデルは同じ知識の穴を持つため、
> 本当に独立した視点が要る局面では、別モデルでのレビューや人間のレビューが必要になる。
> AI レビューの指摘は、可能な限りテスト・動作確認で裏取りして初めて事実になる。

## 領域横断（すべての変更で見る）

### 正確性・ロジック

- 変更は意図した振る舞いを実現しているか。要件・設計ドキュメントと整合しているか。
- 境界値（空・0・最大・null/undefined）の扱いは妥当か。
- 分岐・ループの網羅性。オフバイワン、早期 return の漏れ。
- 例外・エラーの握りつぶしがないか。失敗時に何が起きるか説明できるか。
- 非同期処理の競合・順序・未 await の取りこぼし。
- **データ量が増えた時に壊れないか。** 少数データでは動くが件数・期間・同時実行が増えると
  破綻する処理（部分取得の集計、メモリ蓄積、線形探索の多重）がないか。動作確認で最も見落とす死角。

### 可読性・保守性

- 命名は意図を表しているか。既存コードの命名規則に揃っているか。
- 関数・モジュールの責務は単一か。過度に大きい / 深いネストはないか。
- 重複ロジックを不必要に増やしていないか（逆に、無理な共通化で結合を強めていないか）。
- コメントは「なぜ」を説明しているか（「何を」はコードで語れているか）。
- デッドコード・デバッグ用出力・コメントアウトの残骸がないか。

### セキュリティ

- 外部入力（ユーザー入力・API レスポンス・ファイル・環境変数）を信頼していないか。
- インジェクション対策（パラメータ化クエリ、エスケープ、入力検証）。
- 認証・認可のチェックが必要な箇所で抜けていないか。
- 秘密情報（鍵・トークン・パスワード）がコード・ログ・エラーメッセージに露出していないか。
- 依存追加時：バージョンは固定されているか。名前は typosquatting でないか。保守されているか。

### テスト（網羅の「設計」をレビューする）

テストは正しさの**証拠**になる（実行された事実だから）。ただし証拠の強さはテスト設計の質に
比例する。ここでレビューするのは「テストがあるか」ではなく「**何を網羅し、何を取りこぼしているか**」。

前提として、「網羅」には水準がある。混同しないこと。

- **コードカバレッジ（行・分岐）** … 全行・全分岐を通しただけ。通しただけで値の正しさは別問題。
  **カバレッジ100%は全網羅ではない**。数字を鵜呑みにしない。
- **入力空間の網羅** … 全入力を試す。組み合わせ爆発で現実には不可能。
- **同値分割 + 境界値** … 入力を「同じ振る舞いになる集合」に分け、各代表値と境界を突く。
  無限を有限に畳む、実務での現実的な網羅。**ここがテスト設計の主戦場**。

観点：

- **書かれていないテストを探す** — 網羅の穴は「書いたテストの中」ではなく「書かれなかった
  テストの外」にある。カバレッジ数字ではなく、想定から漏れた入力・状況を指摘する。
- **同値分割・境界値** — 空 / 0 / 最大 / null / 想定外の順序など、境界が意識されているか。
- **異常系・エラー経路** — 権限なし、期限切れ、失敗・例外の経路が検証されているか。
- **状態遷移の各経路** — ドメインに状態機械があるなら、許可された遷移・不正遷移の両方が
  テストされているか（例: 差し戻し経路、権限のない主体による遷移の拒否）。
- **競合・冪等性** — 同時実行・リトライで壊れないことが検証されているか（単発実行では表面化しない）。
- **振る舞いを検証しているか** — 実装の内部構造ではなく入出力を検証しているか。
  過度なモックでテストが空洞化していないか。
- **オラクル（期待値）の妥当性** — `expect(x).toBe(500)` の `500` は仕様として正しいか。
  期待値が要件・仕様に紐づいているか。**ここは正誤をコードから判断できないので Question にする**。

> 判定の指針：テストが同値分割・境界・異常系・状態遷移・競合を意識的にカバーし、期待値が
> 仕様に紐づいているなら、その振る舞いは「実行で裏付けられた」と判定に組み込んでよい。
> ただしテストは正しさを**証明**はしない。取りこぼした領域は依然として未検証である。

### 一貫性

- プロジェクトの既存パターン・アーキテクチャに沿っているか。新しい流儀を持ち込んでいないか。
- 依存の方向・レイヤー分離の規約を破っていないか。
- フォーマット・リンタ規約に沿っているか（設定ファイルがあれば従う）。

## フロントエンド

該当の目安：`.ts` / `.tsx` / `.js` / `.jsx` / `.vue` / `.svelte` / `.css` / `app/` / `src/` の UI 層など。

**まず探す規約源**：`.eslintrc*` / `eslint.config.*`、`tsconfig.json`、`package.json` の依存、
`docs/` 配下のアーキテクチャ規約、steering。

### 観点

- **状態管理** — 状態の持ち場所は適切か。不要な再レンダー・過剰なグローバル状態はないか。
- **データ取得** — ローディング / エラー / 空状態を扱っているか。キャッシュ・再取得の整合。
- **型安全** — `any` の乱用、非 null 断言（`!`）の濫用、型の握りつぶしがないか。
- **コンポーネント設計** — 責務分離。表示とロジックの分離。props の妥当性。
- **アクセシビリティ** — セマンティックな要素、代替テキスト、キーボード操作、コントラスト、
  フォーカス管理。ARIA の誤用がないか。
- **パフォーマンス** — 不要な再計算、巨大バンドル、画像最適化、リスト仮想化の要否。
- **依存方向** — レイヤー / モジュール境界の規約（例: FSD の一方向依存、バレルファイル禁止など）を守っているか。

## バックエンド

該当の目安：API ハンドラ・リゾルバー・サーバーロジック・DB アクセス・スキーマ定義・
バッチ / ジョブ・Lambda などの関数。

**まず探す規約源**：API スキーマ（GraphQL / OpenAPI）、DB スキーマ / マイグレーション、
サーバー側リンタ設定、steering。

### 観点

- **入力検証** — 境界での検証はあるか。信頼できない入力をそのまま処理系・DB に渡していないか。
- **外部データを信頼しない** — DB / 別サービスから読んだ値も「外部入力」。型・存在を無防備に
  使っていないか（例: 金額の加算前に数値であることを保証しているか。欠損時に `NaN` や
  意図しない連結にならないか）。スキーマ上必須でも、移行前データや不整合レコードは来うる。
- **認可（エントリポイントまで辿る）** — 操作ごとに「誰が実行できるか」のチェックがあるか。
  権限の昇格経路がないか。**認可はこの関数内だけを見て判断しない**。呼び出し口（API スキーマの
  認可ディレクティブ、ルート/ミドルウェア、ゲートウェイ設定）まで辿り、どの層で誰が担保して
  いるかを確認する。「role 不問」に見えても、それが仕様として正しいか（全員に見せてよいデータか）を
  必ず突き合わせる。
- **データ整合性** — トランザクション境界、冪等性、部分失敗時の状態、リトライ安全性。
- **状態遷移** — ドメインの状態機械（許可された遷移だけを行うか）。不正遷移をブロックするか。
- **集計・件数依存の正確性** — **ページネーション/部分取得は性能ではなく「正確性」の問題**。
  ページ分割される検索（DynamoDB Query の `nextToken`、SQL の LIMIT、API のページング）の
  結果をそのまま集計・合計すると、データが増えた時に**一部が漏れて結果が壊れる**。
  これはデータが少ない間の動作確認では絶対に再現しないため、静的レビューで必ず疑う。
  取得後に言語側で `filter` して絞っている場合、絞る前の件数がページ枠を食う点も見る。
- **クエリ効率** — N+1、インデックス、スキャン範囲。DB 側で絞れる条件を取得後に言語側で
  絞っていないか。
- **決定性** — 集計結果や一覧の順序が非決定的（ハッシュマップのキー順依存など）になっていないか。
  安定した並び順が必要な出力に順序保証があるか。
- **契約** — API スキーマとの整合。後方互換性の破壊がないか（クライアントへの影響）。
- **エラー処理** — 失敗を適切なステータス / エラーで返すか。内部情報を漏らしていないか。
- **ログ** — 追跡に必要なログはあるか。秘密情報や PII を出していないか。

## インフラ

該当の目安：IaC 定義（CDK / Terraform / CloudFormation 等）・CI/CD 設定・
コンテナ / デプロイ設定・環境変数・権限ポリシー。

**まず探す規約源**：IaC のスタック定義、デプロイスクリプト、環境設定ファイル、steering。

### 観点

- **ブラストラディウス** — この変更が影響する範囲は。ライブリソースを壊す・データを失う恐れは。
- **最小権限** — IAM / ロール / ポリシーが過剰な権限を与えていないか。ワイルドカードの濫用。
- **秘密情報の管理** — 鍵・トークンをコードやリポジトリに直書きしていないか。シークレット管理の利用。
- **可逆性** — 変更はロールバック可能か。破壊的変更（リソース置換・削除）を伴わないか。
- **コスト** — 想定外のコスト増（オーバープロビジョニング、消し忘れリソース）はないか。
- **可用性** — 冗長性・バックアップ・タイムアウト・リトライの設定は妥当か。
- **環境差分** — 本番と非本番で設定が意図通り分かれているか。本番へ誤って適用する経路がないか。

## レビュー出力の型（推奨フォーマット）

```
## レビュー結果サマリ
（対象・判定した領域・全体所感を数行で）

## 指摘
### 🔴 Blocker
- [file:line] 指摘内容 / なぜ問題か / 直し方の方向性

### 🟡 Major
- ...

### 🟢 Minor
- ...

### 💬 Question
- ...

## 良かった点
（あれば簡潔に）
```

指摘には可能な限り **ファイルと行**、**理由**、**修正の方向性** を添える。
「悪い」で終わらせず、なぜ・どう直すかまで書くと合意が速い。
