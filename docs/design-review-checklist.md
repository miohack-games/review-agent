# 設計レビュー観点チェックリスト

設計レビューエージェント（`agents/design-review.md`）が参照する観点の一覧です。
人間のレビュアーがそのまま読んでも使えるように書いています。

これはコードレビュー（`docs/review-checklist.md`）とは**対象も基準も違う**チェックリストです。

| | コードレビュー | 設計レビュー（このファイル） |
|---|---|---|
| 対象 | 実装差分・コード | 設計ドキュメント・要件・スキーマ・仕様 |
| 基準 | 仕様に照らして実装が正しいか | **仕様そのもの**が妥当・網羅・無矛盾か |
| オラクル（正しさの基準） | 仕様を所与とする | **オラクルの空白・矛盾を炙り出す**のが仕事 |
| 実行での裏取り | テストで可能 | まだコードが無いので不可。人間の判断に返す |

---

## この層の役割と限界

**役割** — 実装が始まる前に、仕様そのものを別の視点で叩く。下流（実装・コードレビュー）で
共有されてしまう誤りの多くは、上流の設計の欠陥に由来する。その発生源を上流で減らす。

**できること** — 「ここは誰も正しさを決めていない」「ここの定義が矛盾している」という
**空白と矛盾の検出**。これは網羅的・機械的にやるほど価値が出る（人間より疲れず全箇所を見れる）。

**できないこと** — 「何が正しいか（オラクルの正解）」の決定。仕様に書かれた正解が現実の要求と
ズレている場合の判定。これらは人間の合意領域。**炙り出して人間に返すまでが仕事で、
正解を勝手に決めない。** 決めてしまえば、それは「エージェントが勝手に作ったオラクル」になる。

> ⚠️ 設計レビューエージェントも同系統の AI である以上、仕様の背後にある「本当の要求」との
> ズレは見抜けない。この層は自己検証バイアスを消すのではなく、**誤りの源を上流で減らす**もの。
> 最終的な妥当性の判断は、必ず人間のレビューゲートに残す。

---

## 使い方

1. レビュー対象（設計書・要件・スキーマ・ADR など）と、その上位にある基準
   （プロダクト定義・要件・用語定義）を把握する。
2. まず「オラクルの健全性」を見る（空白・矛盾・測定可能性）。
3. 次に「設計の妥当性」を見る（網羅・整合・非機能・リスク）。
4. 正誤を判定できないものは、勝手に決めず 💬 Question として人間に返す。

指摘は重大度を添えて分類する。

| 重大度 | 意味 |
|--------|------|
| 🔴 Blocker | この設計のまま実装すると破綻する（オラクル欠落・重大な矛盾・データ破壊の設計） |
| 🟡 Major | 実装前に埋めるべき穴（境界・異常系の未定義、非機能の欠落） |
| 🟢 Minor | 改善提案（表現の曖昧さ、整理の余地） |
| 💬 Question | 正誤を判定できず、人間の意思決定が必要なもの（オラクルの正解、要求との整合） |

**重大度の重み付け指針**

- **正確性に影響する非機能の空白は Blocker 候補**。非機能を「性能（速さ）」の話だと矮小化しない。
  例えば集計・合計処理でデータ量の上限が未定義な場合、それは速さの問題ではなく
  **結果の金額・件数が壊れる正確性の問題**であり、実装で固定される前に潰す価値が高い。
- **「実装バグとして顕在化しやすい種類の空白」は強めに警告する**。ページ分割された検索結果の
  集計、同時実行、境界での丸め・切り捨てなどは、実装で素直に書くとバグになりやすい定番。
  設計に前提が書かれていなければ、Minor に流さず Major 以上で挙げる。
- 逆に、粗探しで無理に指摘を作らない。空白が無ければ「問題なし」と明記してよい。
  設計の質が高いこと自体は正しく評価する。

## レビューの姿勢（自己検証バイアスと一貫性への対策）

設計書は「これで問題ない」と主張するために書かれている。その主張に引きずられると、
空白を空白として見られなくなる。次の姿勢で緩和する。

### 1. 設計書の断定を、結論ではなく検証すべき主張として扱う

「件数は小さいので性能問題なし」「このケースは起きない」「合意済み」といった断定を
**根拠として受け取らない**。その主張が本当に成り立つか、**反例や前提の抜けを1つ探す**。
特に「問題なし」の主張は、根拠（想定件数・前提条件）が示されているかを確認し、
根拠が無い断定は Question にする。楽観的な前提こそ、実装で最も高くつく空白になる。

### 2. 複数の視点で一巡する

- **攻撃者・不正利用の視点** — 権限・入力・順序を悪用して、この設計で守れないものはないか。
- **データが桁違いに増えた視点** — 自動生成・繰り返し・複数主体で、この設計は成り立つか。
- **引き継ぐ人の視点** — この設計書だけを渡された実装者が、迷わず一意に実装できるか
  （迷う所があれば、それはオラクルの空白）。

### 3. 適用範囲を自己申告する

レビューの冒頭または末尾で、**突き合わせた上位基準と、見た観点・見ていない観点**を明示する
（例:「要件書とプロダクト定義に照らし、オラクルの空白と非機能を見た。他プロダクトとの整合は未確認」）。
レビューのブレを可視化し、人間が見落とし範囲を把握できるようにする。

> これらは自己検証バイアスを**消す**ものではない。設計レビューエージェントも同系統の AI であり、
> 仕様の背後にある「本当の要求」とのズレは見抜けない。本当に独立した視点が要る局面では、
> 別モデルでのレビューや人間の判断が必要になる。

## A. オラクルの健全性（この層の主戦場）

「何をもって正しいとするか」が、実装前にきちんと決まっているかを見る。

### 空白を探す — 仕様が沈黙している所

- **未定義の入力・状態** — 空 / 0 / 上限超過 / null / 期限切れ / 権限なし などに対する
  期待挙動が定義されているか。「正常系しか書いていない」設計は、境界・異常系が空白のまま。
- **未定義の組み合わせ** — 複数の状態・役割・条件が重なったときの挙動が決まっているか
  （例: 同時実行、複数の主体が同じ操作、状態Aかつ条件Bのとき）。
- **暗黙のデフォルトの是非** — 「決めていないから適当に埋める」箇所がないか。
  それが**仕様上の意図的な決定**なのか、単に**決め忘れ**なのかを確認する（後者は Question）。
- **例：** 「表示名を月の途中で変えたら、集計にはどちらの名前を出すか」が仕様に無い、など。
  こうした沈黙は、実装者が勝手に埋めてしまう前に指摘する。

### 矛盾を探す — 正しさが食い違っている所

- **用語・定義の揺れ** — 同じ概念が場所によって違う意味で使われていないか
  （用語集があれば突き合わせる）。
- **基準どうしの衝突** — ある受け入れ基準と別の基準が両立しない状況がないか。
- **上位仕様との不整合** — プロダクト定義・要件が目指す価値と、この設計が矛盾していないか。

### 測定可能性 — オラクルとして機能するか

- **受け入れ基準がテスト可能な形か** — 曖昧な形容詞（速い・使いやすい）でなく、測れる条件か。
  ここが曖昧だと、下流でどれだけテストを厚くしても正しさを裏取りできない。
- **各設計要素が、どの受け入れ基準を満たすために存在するか**を辿れるか（要件へのトレーサビリティ）。

---

## B. 設計の妥当性

オラクルが健全である前提で、設計そのものの質を見る。

### 網羅

- **状態遷移の網羅** — ドメインに状態機械があるなら、許可された遷移・不正遷移・
  各遷移を実行できる主体（権限）がすべて定義されているか。抜けた遷移は実装で事故になる。
- **エラー・失敗経路** — 失敗時にどうするか（リトライ・ロールバック・ユーザー通知）が
  設計されているか。ハッピーパスだけになっていないか。

### 整合

- **既存アーキテクチャとの整合** — 構造方針・レイヤー・依存の向きに沿っているか。
- **契約（API・スキーマ）の整合** — 入出力の型・必須/任意・後方互換性が定義されているか。

### 非機能（下流バグの上流での予防）

- **データ量・負荷の増加に耐えるか** — 「少数データでは動くが、件数・期間・同時実行が
  増えると壊れる」設計になっていないか。**集計・一覧・検索は、ページ分割/部分取得を
  前提に設計されているか**（これを設計段階で問えれば、実装のページネーション漏れバグ自体が
  生まれない。＝上流で源を断つ）。
- **データ量の現実的な上限を、上位仕様まで辿って見積もる** — 「件数は小さいので問題なし」と
  設計が主張していても、それを鵜呑みにしない。**自動生成・定期バッチ・繰り返し処理・
  複数主体の掛け算**でデータは想定以上に増える。対象の集計・一覧が扱うデータの上限を、
  関連する上位仕様（スケジュール自動生成、定期ジョブ、繰り返し設定など）まで読んで見積もり、
  その上限でも設計が成り立つかを確認する。「性能問題なし」の主張の根拠（想定件数）が
  示されているか、その想定が上位仕様と整合しているかを見る。
- **性能・可用性・整合性** — レイテンシ目標、冪等性、トランザクション境界、
  同時実行時の一貫性が設計に含まれているか。
- **セキュリティ・認可の設計** — 「誰が何をできるか」が設計レベルで定義され、
  データの公開範囲が仕様と一致しているか。

### リスク・未確定事項

- **未検証の前提（PoC が要る所）** — 「満たせそう」で止まっている技術的前提はないか。
- **リスクと未確定事項が明記されているか** — 設計書に「分かっていないこと」が
  正直に書かれているか。書かれていない不確実性は、後で最も高くつく。

## 出力の型（推奨フォーマット）

```
## 設計レビュー結果サマリ
（対象・突き合わせた上位基準・全体所感を数行で）

## オラクルの健全性
### 🔴 Blocker（正しさの基準が欠落・矛盾）
- [箇所] 何が空白/矛盾か / なぜ実装前に埋める必要があるか
### 🟡 Major
- ...

## 設計の妥当性
### 🟡 Major / 🟢 Minor
- ...

## 人間の判断が必要な事項（Question）
- [箇所] 正誤を判定できない理由 / 誰が何を決める必要があるか

## 良かった点
（あれば簡潔に）
```

指摘には可能な限り、設計書・要件の**該当箇所**と、**なぜ実装前に解消すべきか**を添える。
Question は「決めておくべき問い」の形で、誰が何を決めるのかまで書くと、人間が判断しやすい。
