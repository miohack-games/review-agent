# review-agent

> どのリポジトリでも使える、コードと設計のための汎用レビュー用 Kiro カスタムエージェント。

言語・フレームワークに依存しない、**汎用レビュー用の Kiro カスタムエージェント**一式です。
特定プロジェクトに固定せず、どのリポジトリでもレビューに使えることを目指しています。

2 つのレビューエージェントを、レビューする対象で使い分けます。

| エージェント | 対象 | 見るもの | 使うタイミング |
|--------------|------|----------|----------------|
| `code-review` | 実装差分・コード | 仕様に照らして実装が正しいか | 実装後・PR 前 |
| `design-review` | 設計書・要件・スキーマ | **仕様そのもの**が妥当・網羅・無矛盾か | 実装前・設計レビュー時 |

## 何のためのものか

これらのエージェントは、レビューを人間から奪うためのものではありません。
**人間が見る量を減らし、見るべき所（意図・価値判断・最終承認）に集中させる**ためのものです。

- レビューが機械的・規約的な指摘を先に潰す（人間の負荷を下げる）
- 人間はレビューゲートそのもの（合意と承認）に集中する

AI による自己検証には限界があります（実装したのと同質の AI がレビューすると、同じ見落としを
共有しがち）。だからエージェントは読み取り専用に徹し、白黒つけにくい判断は Question として
人間に委ねる設計にしています。最終的な「正しさ」を保証するのは人間です。

### 2 層に分ける理由

コードレビューは「仕様が正しい」を前提にするため、仕様そのものの齟齬・空白は直せません。
そこで、実装が始まる前に仕様を別視点で叩く **`design-review`** を上流に置きます。

- `design-review` … オラクル（何をもって正しいとするか）の**空白・矛盾**を炙り出す。
  下流で共有されてしまう誤りの源を、実装前に減らす。
- `code-review` … 仕様を所与として、実装がそれを満たすかを見る。疑いはテストで裏取りできる。

どちらも「正しさそのもの」は決めず、人間が判断すべき事項を Question として返します。

## 設計方針

汎用性を保つために、意図的にこう作っています。

- **プロジェクト固有のパスを埋め込まない** — 「フロントならこのファイル」を固定しない。
  代わりに、エージェントが実行時にプロジェクト構成を調べ、規約源（steering / `AGENTS.md` /
  `CONTRIBUTING.md` / リンタ設定など）を自分で探して読む。
- **領域を動的に判定** — 変更ファイルから フロント / バック / インフラ を判定し、
  該当領域の観点を重ねる。
- **プロジェクト規約を最優先** — 汎用チェックリストより、そのリポジトリ自身の規約を優先する。
- **読み取り専用・破壊操作禁止** — 書き込み、コミット、デプロイ、`rm`/`sudo` などは
  権限ルールでブロック。レビュー中に事故が起きない。
- **自己検証バイアスへの姿勢を組み込む** — 実装者の「大丈夫」という断定を検証すべき仮説として
  扱い、攻撃者・大規模データ・引き継ぎ者の複数視点で一巡し、適用した観点を自己申告する。
  各チェックリストの「レビューの姿勢」に定義。

## AI レビューの限界（過信しないための前提）

このエージェントは有用だが、万能ではない。次の限界を理解して使う。

- **自己検証バイアスは完全には消えない。** AI が実装したものを同系統の AI がレビューすると、
  同じ知識の穴・同じ盲点を共有する。プロンプトの工夫（反証・視点多様化）で緩和できるが、
  構造的にゼロにはできない。本当に独立した視点が要る局面では、**別モデルでのレビュー**
  （各エージェント定義のフロントマターに `model:` を指定して使い分け）や、**人間のレビュー**が要る。
- **AI レビューは一貫しない。** 同じ差分でも指摘がぶれる。判定基準をチェックリストに外部化し、
  手順を固定し、適用範囲を自己申告させることでブレを減らしているが、決定論にはならない。
  **だから 1 回のレビューを信じきらず、指摘はテスト・動作確認で裏取りする。**
- **正しさそのものは決められない。** オラクル（何が正しいか）の正解、仕様と本当の要求のズレは、
  人間の合意領域。エージェントは「人間が判断すべき一点」を炙り出すところまでが役割。
- 結論として、これは**人間のレビューゲートを置き換えるものではなく、その手前で負荷を下げ、
  見るべき所を炙り出す道具**である。

## 構成

```
review-agent/
├── README.md                       ← このファイル
├── agents/
│   ├── code-review.md              ← コードレビューエージェント（Kiro カスタムエージェント定義）
│   └── design-review.md            ← 設計レビューエージェント（同上）
└── docs/
    ├── review-checklist.md         ← コードレビュー観点（code-review が参照。人間も読める）
    └── design-review-checklist.md  ← 設計レビュー観点（design-review が参照。人間も読める）
```

## 導入手順

Kiro のカスタムエージェントは、次のいずれかに置くと認識されます。

- グローバル（全プロジェクトで使える）：`~/.kiro/agents/`
- ワークスペース（そのリポジトリ専用）：`<workspace>/.kiro/agents/`

汎用に使いたいので、**グローバル配置**を推奨します。

### 1. エージェント定義とチェックリストを配置する

2 つのエージェント定義と、それぞれが参照するチェックリストを `~/.kiro/agents/` に置きます。

各エージェント定義内の `resources` は `file://docs/...-checklist.md` という相対参照で、
エージェント定義ファイルからの相対で解決されます。次のどちらかにします。

- **推奨**：`~/.kiro/agents/` の下に `docs/` も配置し、相対関係を保つ。

  ```
  ~/.kiro/agents/
  ├── code-review.md
  ├── design-review.md
  └── docs/
      ├── review-checklist.md
      └── design-review-checklist.md
  ```

- あるいは各 `resources` の行を、置いた場所に合わせた絶対 `file://` パスに書き換える。

PowerShell での配置例（このリポジトリを clone / 配置済みとして）:

```powershell
$dst = "$env:USERPROFILE\.kiro\agents"
New-Item -ItemType Directory -Force -Path "$dst\docs" | Out-Null
Copy-Item -Path ".\agents\code-review.md"   -Destination $dst -Force
Copy-Item -Path ".\agents\design-review.md" -Destination $dst -Force
Copy-Item -Path ".\docs\review-checklist.md"        -Destination "$dst\docs" -Force
Copy-Item -Path ".\docs\design-review-checklist.md" -Destination "$dst\docs" -Force
```

> チェックリストが読み込めない場合でも、各エージェントは代替として基本的な観点で
> 動作するフォールバックを持っています。ただし観点の網羅性は下がるため、
> `resources` は解決できる状態にしておくことを推奨します。

### 2. エージェントを選ぶ

Kiro のチャット入力欄の下部にあるエージェント名（既定は「Default」）をクリックすると
エージェントピッカーが開きます。対象に応じて `code-review` か `design-review` を選びます。
次のメッセージから現在のセッションに適用されます。

### 3. レビューを依頼する

**コードレビュー（`code-review`）** — 対象を伝えるだけです。指定がなければ未コミットの差分を対象にします。

- 「今の変更をレビューして」
- 「このPRの差分を見て」（`gh` が使える環境なら PR も対象にできます）
- 「src/features/... のこのファイルをレビューして」

**設計レビュー（`design-review`）** — レビューする設計・要件ドキュメントを伝えます。

- 「この設計書をレビューして」（実装前）
- 「この要件の受け入れ基準に抜けがないか見て」
- 「この機能仕様で、決め切れていない挙動を洗い出して」

## チーム共有

ワークスペースの `.kiro/agents/` に置いてリポジトリにコミットすれば、チーム全員が同じ
レビューエージェントを使えます。レビュー観点（`docs/review-checklist.md`）を育てていくことで、
チームのレビュー品質を均一化できます。

## カスタマイズ

- **観点を足す / 変える** — `docs/review-checklist.md`（コード）や
  `docs/design-review-checklist.md`（設計）を編集する。各エージェントはこれを基準に見ます。
- **許可コマンドを調整する** — 各エージェント定義（`agents/*.md`）の `permissions.rules` を編集する。
  デフォルトは読み取り・解析系のみ許可、破壊系は拒否。
- **モデルを固定する** — フロントマターに `model:` を追加できます（未指定なら既定モデル）。
- **ショートカット** — フロントマターに `keyboardShortcut:` を追加すると素早く切り替えられます。
